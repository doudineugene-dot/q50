# Контейнер `.epk` головного устройства Q50

Формат разобран полностью. Раскладка подтверждена двумя независимыми
источниками, которые сошлись:

1. **Имена и порядок полей** — из декомпилированного парсера IVI
   `com.connexis.ivi.utils.epk.v2`, класс `EpkParseResult.EpkEntry.Envelope`.
   Источник: [oneezeeroo/Q50-Reverse-Engineering](https://github.com/oneezeeroo/Q50-Reverse-Engineering).
2. **Точные смещения и длины** — разбором образцов `gtr.epk` (2 156 912 байт)
   и `appgarage-dash-v1.0.epk` (25 456 байт) от разных авторов.

Сходимость: заявленная в заголовке длина нагрузки плюс смещение её начала
дают размер файла **до байта**, а сама длина кратна 16. Гадать не пришлось.

## Раскладка

```
смещение  размер  поле            значение в gtr.epk
--------  ------  --------------  --------------------------------
0x000        4    m_magicCode     ".epk"
0x004        2    m_version       2            u16 BE
0x006        2    m_payloadType   2            u16 BE
0x008        2    m_blockCount    1            u16 BE — число записей
0x00A        2    m_keySize       128          u16 BE — значащих байт в m_key
0x00C      256    m_key[256]      буфер фиксированной длины
------------------ конец конверта, 268 байт ---------------------
0x10C      128    имя файла       "gtr.apk", ASCIIZ
0x18C        4    длина нагрузки  2 156 512    u32 BE
0x190      ...    нагрузка        зашифрована
```

Сверка: `0x190 + 2 156 512 = 2 156 912` = размер файла. `2 156 512 / 16 = 134 782`.

## Что такое `m_key`

Это **самое важное** в формате, и в исходном исследовании этот вопрос стоял
открытым («What does the 256-byte key field represent?»).

Буфер фиксированный, 256 байт, но значащих в нём `m_keySize` = **128 байт =
1024 бита**. Это ровно размер шифротекста RSA-1024. Остальные 128 байт —
нули, что и подтверждается образцом.

Отсюда схема гибридная, как в любом нормальном контейнере:

```
нагрузка  --- зашифрована симметрично (AES)
            ^
            |
ключ AES  --- завёрнут в RSA-1024 и лежит в m_key
```

То есть **ключ шифрования нагрузки лежит прямо в файле**, но завёрнут. Чтобы
его развернуть, нужен **закрытый ключ RSA из прошивки головного устройства**.

Это меняет цель поиска: искать надо не статический AES-ключ, а закрытый ключ
RSA либо код в IVI, который выполняет разворот.

## Признаки шифрования нагрузки

| Проверка | Результат |
|---|---|
| Сигнатуры ZIP в нагрузке | нет ни одной |
| Энтропия | 8.000 из 8.0 |
| Повторы 16-байтных блоков | 0 из 134 782 — режим не ECB |
| Кратность 16 | да — блочный шифр |

Режим (CBC или CTR) и IV по одному образцу не определить. Понадобится либо
второй файл, либо код IVI.

## Проверка на втором образце

Формат разобран на двух контейнерах **разных авторов**, и раскладка совпала
полностью — значит она свойство формата, а не особенность одного файла.

| | `gtr.epk` | `appgarage-dash-v1.0.epk` |
|---|---|---|
| размер файла | 2 156 912 | 25 456 |
| `m_version` | 2 | 2 |
| `m_payloadType` | 2 | 2 |
| `m_blockCount` | 1 | 1 |
| `m_keySize` | 128 | 128 |
| вложенное имя | `gtr.apk` | `dash.apk` |
| длина нагрузки | 2 156 512 | 25 056 |
| начало данных | `0x190` | `0x190` |
| сверка длины | сходится | сходится |

## Криптоанализ: что исключено

Сравнение двух образцов закрывает все дешёвые пути:

| Проверка | Результат | Что исключает |
|---|---|---|
| Повторы 16-байтных блоков внутри файла | 0 | режим ECB |
| Совпадение `m_key` | 0 общих байт из 128 | общий ключ на все пакеты |
| Общий префикс шифротекстов | 0 байт | одинаковый ключ **и** IV |
| Энтропия XOR двух шифротекстов | 7.9922 из 8.0 | повтор гаммы (CTR/OFB) |

Последняя строка — самая содержательная. Если бы два пакета шифровались одной
гаммой, то `C₁ xor C₂ = P₁ xor P₂`, и XOR двух ZIP-архивов дал бы заметно
неслучайный результат. Энтропия 7.9922 означает, что этого нет.

Вывод: **у каждого пакета свой случайный сеансовый ключ**, завёрнутый в RSA.
Это корректно реализованная гибридная схема, без слабых мест, за которые можно
зацепиться. Единственный путь — закрытый ключ RSA из прошивки.

Проверить это на новых образцах:

```bash
tools/epktool.py compare файл1.epk файл2.epk
```

## Установка: только через .epk

Подтверждено на практике: **головное устройство не распознаёт голый APK.**
Ни через USB, ни через штатный установщик — приложение принимается только
упакованным в `.epk`. Значит собрать контейнер обязательно, обойти его нечем.

## Два ключа — две разные задачи

Расшифровка чужого пакета и сборка своего требуют РАЗНЫХ ключей.

| Задача | Нужен | Как в epktool |
|---|---|---|
| Собрать свой `.epk` для установки | **публичный сертификат OBU** | `pack --rsa-pub obu-cert.pem` |
| Распаковать чужой `.epk` | закрытый ключ DCU | `extract --rsa-key dcu-priv.pem` |

Роли ключей (по словам энтузиаста, собиравшего пакеты):

- **OBU** (On-Board Unit) — головное устройство. Его **публичный сертификат**
  и есть всё, что нужно для создания EPK. Сеансовый ключ AES заворачивается
  открытым ключом из этого сертификата.
- **DCU** — сторона с **закрытым** ключом. Он производителю нужен для своих
  операций, но **для сборки устанавливаемого пакета не требуется**.

Это и подтверждает найденную схему: `m_key` — сеансовый ключ AES, завёрнутый
открытым ключом OBU. Чтобы завернуть — достаточно публичного сертификата.
Именно поэтому свои `.epk` вообще можно собирать: секрет производителя (закрытый
ключ DCU) в этом не участвует.

### Сертификат, а не голый ключ

Публичный OBU — это **X.509-сертификат**, а не файл открытого ключа. Открытый
ключ RSA лежит внутри него. `epktool` принимает сертификат напрямую, в PEM или
DER: `--rsa-pub obu-cert.pem`. Отдельно извлекать ключ не нужно.

## Инструмент проверен сквозным тестом

На собственной паре ключей RSA-1024 полный цикл проходит без потерь:

```
APK --pack --rsa-pub--> .epk --extract --rsa-key--> APK
```

Результат: собирается корректный конверт формата ГУ (version 2, payload_type 2,
m_keySize 128, данные с 0x190), а извлечённый APK совпадает с исходным
**байт в байт**. Оба пути RSA — разворот закрытым ключом и сырой разворот
открытым — тоже проверены.

Проверено, что `--rsa-pub` принимает и голый ключ, и X.509-сертификат (PEM и
DER) — цикл через сертификат тоже даёт APK байт в байт. Значит инструмент готов
заранее: как только появится публичный сертификат OBU, сборка устанавливаемого
пакета — одна команда.

## Что это значит для своей сборки

`epktool.py pack` собирает контейнер правильной раскладки, но поле `m_key`
оставляет нулевым: завернуть симметричный ключ можно только **открытым**
ключом IVI, которого тоже нет.

Пока не найден хотя бы один из двух ключей — открытый для упаковки или
закрытый для распаковки — установить своё приложение этим путём нельзя.

## Утилита

```bash
tools/epktool.py info gtr.epk
tools/epktool.py extract gtr.epk -o payload.bin              # сырой шифротекст
tools/epktool.py extract gtr.epk -o gtr.apk --rsa-key ivi.pem
tools/epktool.py extract gtr.epk -o gtr.apk --key <hex> --mode cbc
tools/epktool.py pack q50info.apk -o q50info.epk
```

## Что известно о платформе

Из того же исследования:

- Q50 IVI — гибрид: Linux плюс **сильно изменённый Android 2.3**. Это
  подтверждает выбор `minSdk 9` для нашего приложения.
- Обычный путь установки APK не работает: обработка EPK встроена в IVI,
  а не наследуется от Android.
- Предполагаемая цепочка установки:
  `APK -> упаковка в EPK -> подпись/проверка -> USB-менеджер -> установка IVI`.
